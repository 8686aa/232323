# UDP 投屏协议 v1.0

三端字节级一致，任何一端改动都必须同步修改另外两端：

| 端 | 文件 |
| --- | --- |
| Android 发送 | `android/app/src/main/java/com/udpcast/sender/CastProtocol.kt` |
| iOS 发送 | `ios/UdpCast/Shared/CastProtocol.swift` |
| PC 接收 | `receiver/receiver.py` |

---

## 1. 为什么选「裸 H.264 over UDP」而不是 WebRTC / RTSP

| 方案 | 依赖 | 实现复杂度 | 局域网延迟 | 适用性 |
| --- | --- | --- | --- | --- |
| 本项目 | 仅系统 API | 低 | 最低（无拥塞控制排队） | 可信局域网、一发多收、要极简 |
| WebRTC | 需要完整协议栈 | 高 | 低 | 需要公网穿透 / NAT 穿越 |
| RTSP + RTP | 需要服务端与协商 | 中 | 中 | 需要标准播放器直接打开 |

局域网场景下带宽充足、丢包极低，UDP 裸传 H.264 能把延迟压到最低，且代码量小、三端都能快速实现。

---

## 2. 分层结构

```
  ┌──────────────────────────────────────────────┐
  │  屏幕帧 (MediaProjection / ReplayKit)         │
  └───────────────────┬──────────────────────────┘
                      ▼
  ┌──────────────────────────────────────────────┐
  │  H.264 硬编码 (MediaCodec / VideoToolbox)     │
  │  输出 Annex-B 裸流，关键帧自带 SPS/PPS        │
  └───────────────────┬──────────────────────────┘
                      ▼
  ┌──────────────────────────────────────────────┐
  │  分片层（本协议）：一帧切成多个 UDP 数据报     │
  └───────────────────┬──────────────────────────┘
                      ▼
  ┌──────────────────────────────────────────────┐
  │  UDP 到接收端（无重传、无拥塞控制）            │
  └──────────────────────────────────────────────┘
```

协议只解决「把一帧 H.264 数据可靠地切片、编号、标识」，不做重传。

## 3. 单个 UDP 数据报布局

固定 16 字节包头 + 负载，**全部大端序（Big-Endian）**。

| 偏移 | 长度 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- | --- |
| 0 | 4 | `magic` | bytes | 固定 `0x55 0x44 0x50 0x31`，即 ASCII `"UDP1"` |
| 4 | 4 | `frameId` | uint32 | 单调递增；同一帧的所有分片共享同一个值 |
| 8 | 2 | `packetIndex` | uint16 | 本分片在该帧内的序号，从 0 开始 |
| 10 | 2 | `packetCount` | uint16 | 该帧的分片总数（≥1） |
| 12 | 1 | `flags` | uint8 | 见下表 |
| 13 | 1 | `reserved` | uint8 | 固定 `0x00`，接收端忽略 |
| 14 | 2 | `payloadLen` | uint16 | 负载字节数，≤ 1384 |
| 16 | N | `payload` | bytes | H.264 Annex-B 裸流片段 |

C 结构体等价形式：`struct.pack(">4sIHHBBH", ...)`，`calcsize == 16`。

### 3.1 flags 位定义

| 位 | 值 | 名称 | 含义 |
| --- | --- | --- | --- |
| bit0 | 0x01 | `KEYFRAME` | 该帧是 IDR，且 payload 已前置 SPS/PPS，可独立解码 |
| bit1 | 0x02 | `CONFIG` | 纯编解码器配置（当前实现不单独使用，SPS/PPS 直接并入关键帧） |
| bit2 | 0x04 | `END` | 帧结束标记（保留，当前未使用） |

## 4. 分片规则

- `MTU = 1400` 字节（含包头），`MAX_PAYLOAD = 1384` 字节。
  1400 可安全穿过以太网 / Wi-Fi 的 1500 MTU，不产生 IP 分片。
- 一帧切分成 `ceil(len / 1384)` 个数据报。
- **不跨帧合并**：一个数据报的负载只来自一帧。

### 4.1 关键帧自带 SPS/PPS（抗丢包的核心）

编码器输出的 `CODEC_CONFIG`（SPS/PPS）被发送端缓存，在每个关键帧发送时**前置拼接到该帧数据前面**，作为同一个逻辑帧发送。

这样每个关键帧都是一个可独立解码的完整单元：

```
关键帧 payload = [00 00 00 01 SPS][00 00 00 01 PPS][00 00 00 01 IDR ...]
普通帧 payload = [00 00 00 01 ...P...]
```

**接收端因此不需要实现 NACK、重传或参考帧管理**：一旦丢包导致花屏，最多等一个 I 帧间隔（默认 2 秒）就自动恢复。

## 5. 接收端重组规则

1. 校验 `magic`，不匹配则丢弃。
2. 以 `frameId` 为键建桶，按 `packetIndex` 填充。
3. 当 `len(parts) == packetCount` 时帧完整，放入「待输出」缓冲区。
4. **按 frameId 顺序输出**，保证送给解码器的码流帧序正确。
5. 出现空洞时的处理：
   - 收到**关键帧**时立即强制推进（跳过空洞），因为关键帧不依赖前序参考帧；
   - 空洞超过 `MAX_PENDING_FRAMES`（64）帧时强制推进；
   - 单帧超过 `FRAME_TIMEOUT`（1.5 秒）未收全 → 丢弃并标记，迟到的重复分片被忽略。

### 5.1 frameId 回绕

`frameId` 是 uint32，按 `& 0xFFFFFFFF` 递增。接收端比较帧序时使用环形差值 `(a - b) & 0xFFFFFFFF`，不做简单大小比较。

## 6. 接收端发现协议

发送端在不知道 PC 地址时可主动广播搜索：

| 方向 | 端口 | 内容 |
| --- | --- | --- |
| 发送端 → 广播地址 | UDP 5001 | ASCII `UDPCAST_DISCOVER` |
| 接收端 → 发送端源地址 | UDP（回包到源端口） | ASCII `UDPCAST_HERE:<主机名>` |

发送端收到以 `UDPCAST_HERE` 开头的响应后，取该数据报的源 IP 作为接收端地址。

> 注意：部分企业 AP 开启了客户端隔离（AP Isolation）会拦截广播。发现失败时手动填写 IP 即可，不影响投屏。

## 7. 已知限制

- **无重传**：丢包即丢帧。局域网内实测丢包率通常 < 0.1%，画面自愈依赖 I 帧。
- **无加密**：数据明文传输，请只在可信局域网使用。需要加密可以在包头之后加一层 AES-GCM。
- **无音频**：v1.0 只投画面。
- **单接收端**：当前发送端把数据发往单一目标地址。要做一发多收，把发送端的目标地址换成组播地址（如 `239.1.1.1`）即可，协议本身无需改动。
